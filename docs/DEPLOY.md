# Deploying to production

The app runs on Vercel and talks to one hosted Supabase project. Nothing here needs a secret in
the repository: keys live in Vercel environment variables and in the Supabase vault.

## 1. Vercel environment variables

Set them on the Vercel project that serves the public domain, for the Production environment.
`NEXT_PUBLIC_*` values are baked in at build time, so redeploy after changing them.

| Variable | Required | Notes |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | yes | Project API URL. |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` or `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | yes | Either name works. |
| `SUPABASE_SERVICE_ROLE_KEY` or `SUPABASE_SECRET_KEY` | yes | Server only. Sign-up, photo upload, account deletion and cron need it. |
| `NEXT_PUBLIC_SITE_URL` | no | Defaults to the Vercel production URL. Set it for a custom domain. |
| `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, `NEXT_PUBLIC_VAPID_PUBLIC_KEY` | no | Web push. Without them the app works and sends no push. |
| `CRON_SECRET` | no | Only if you prefer an env secret. By default the cron secret is verified in the database (see below). |

The Supabase integration for Vercel sets the first three for you, but only on the Vercel project
it is connected to. Check with `GET /api/health`: it answers booleans only.

```json
{ "ok": true, "config": { "url": true, "publicKey": true, "serviceKey": true }, "schema": true }
```

`config.*` false means the variable is missing in that deployment. `schema` false means the
database has no tables yet (migrations not applied) or cannot be reached.

## 2. Database

Apply `supabase/migrations/0001` to `0021` in order, as the `postgres` role, to an empty project.

Never apply `supabase/seed.sql` to production: it creates test users with a known password.
Never run `supabase db reset --linked`, `supabase db push --include-seed` or
`supabase config push` against the hosted project, and never run the end-to-end suite with
hosted keys.

After the migrations:

```sql
-- the site origin the cron job calls (not a secret); once per environment
select vault.create_secret('https://your-domain.example', 'app_url');

-- checks
select count(*) from supabase_migrations.schema_migrations;          -- 21
select jobname, schedule, active from cron.job;                       -- kizuna-cron, every 15 minutes, active
select id, public from storage.buckets;                               -- avatars (public), proofs (private)
select count(*) from vault.secrets where name in ('app_url', 'cron_secret');  -- 2
```

The secret the cron job presents (`cron_secret`) is generated by migration 0020 and verified by
the app through the database, so it never has to be copied by hand. To rotate it:
`select vault.update_secret(id, encode(extensions.gen_random_bytes(32), 'hex')) from vault.secrets where name = 'cron_secret';`
(it must stay 64 lowercase hex characters).

## 3. Supabase Auth settings

| Setting | Value | Why |
| --- | --- | --- |
| Allow new users to sign up | off | The app creates accounts from the server after its own validation and rate limit. Leaving the public endpoint open only lets someone bypass those. |
| Confirm email | either | Sign-up does not depend on it. |
| CAPTCHA | off | The app does not send a CAPTCHA token yet; turning it on breaks sign-up and login. |
| JWT signing keys | asymmetric (optional) | With asymmetric keys the session is verified locally and every page is faster. With the legacy secret it still works, one Auth call per request. |

## 4. Verify the deployment

1. `/api/health` answers `"ok": true`.
2. Open `/bienvenida`, create an account, and land on the account-ready screen.
3. Sign out and sign in again with the handle and with the e-mail.
4. Check in a habit, add a photo check-in, and open Resumen.
5. In the SQL editor: `select count(*) from net._http_response where created > now() - interval '1 hour';`
   grows every 15 minutes (the cron job is calling the app), and the cron routes answer 200.

## 5. Known gaps

- No password recovery and no e-mail verification (accounts are created without a confirmation e-mail by design).
- Web push needs the VAPID keys above.
- Photos are limited to 4 MB per upload (Vercel rejects larger request bodies).
- The cron routes have no rate limit of their own.
